# 音量係数のべき乗と1サンプル差の修正

2026-10-13。葵seed19 case117で残っていたPCM16の1サンプル差を、通常SDKとの比較で解消した。文章は `火閉漢字私六零四木1月78金土Ｂ六火A火三。`。修正後の675304バイトのWAV全体が原版・独立したSDK採取と一致し、SHA256は `28769406e32b762f656dc0e32999637fe061ae7e9cf7cb3e63eca6a9c8819fe5`。[終了済みWAV・演算検証](evidence/magnitude-pow-wav.json)。元の失敗記録も保持する。

原版の圧縮処理は、クリップした音量から指数を作り、固定の底10を使って係数を求める。このモデルの指数範囲は[-5,0]。`torch_cpu.dll` の呼出しを追い、Windows UCRTの `powf` へのインポートを確認した。通常の `math.Pow` をbinary32に変換する方法では、第7回の110指数のうち1個の結果が1ビット違い、圧縮処理の240値と最終PCMの1サンプルへ差が広がった。

原版UCRTのFMA経路をGhidraと逆アセンブルで調べ、底10の対数の計算結果、1/64単位の指数表、範囲縮小、3次多項式、FMAと丸めの順序をGoへ移植した。底10の対数は原版の `40026bb1bbb55515` を使う。正確な数学上の対数への置換は、原版の丸めを変える。`math.FMA` とビット操作で再構築し、Go実行時にUCRTやエンジンDLLをロードしない。

`TestMagnitudePowOriginal` は直接採取した原版関数の全65651組（乱数65536、境界5、実際の第7回の110指数）と比較する。従来の `math.Pow` は5件異なり、新実装は全ビット一致した。原版UCRTはSHA256 `5c52e3a303baaac0e0af8bd9b96134993da34bc9d834a31ef37e1d2cdc7fe192`、`powf` RVA `a9f20`、FMA選択フラグは3。この数値経路の比較であり、未採取のCPU・ランタイムの自動選択完了を意味しない。

`TestCompressorSeed19PowOriginal` は、原版観測時のWAV全体が独立SDK採取と一致した実行から、14回すべての波形・音量入力・出力を通常のDLL不要回帰に固定する。変更前は1回・240値だけ違い、変更後は全334800値が原版と全ビット一致した。残る13回も除外しない。

Windows/Linux amd64・CGO=0・GOAMD64=v1で、この全65651組と全334800値が一致した。既存のAMD圧縮処理13回・285840値とIntelの50160値も両OSで一致し、DSPの全テスト、ONNXの全回帰、静的検査が通過した。

Linuxの同じ文章の両音声WAV再実行も526.24秒で終了し、茜592338バイト・葵675304バイトの全体が原版と一致した。[Linux検証](evidence/magnitude-pow-linux-wav.json)。コミット `c431abd` の変更なしのソースから通常CLIをCGO=0で構築し、埋込み純Go経路の葵のWAV全体も通常SDK・独立採取と一致した。合成中のプロセスの読取り観測では、エンジン・Torch・ONNX RuntimeのDLLが読み込まれていなかった。[CLI検証](evidence/magnitude-pow-cli-wav.json)。

失敗した葵の分割5は全16文章を別の保存先で再比較中。最終seed19の全256音声、数詞の未解決分岐、全CPU・設定の完全一致は別途検証を続ける。再実行の監査は全分割を要求し、元の失敗したレポートとログもSHA256で固定して保存する。
